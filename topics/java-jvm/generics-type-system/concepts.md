# Generics and the Type System

Java generics were introduced in **Java 5 (2004, JSR 14)** as a compile-time mechanism for
parametric polymorphism. They let you write classes, interfaces, and methods that operate over a
*type parameter* (`List<E>`, `Map<K,V>`) so that type safety is checked by the compiler rather than
deferred to run time. Crucially, generics in Java are implemented via **type erasure**: they are a
front-end (compiler) feature and largely vanish from the bytecode. Understanding that single fact
explains almost every "surprising" generics behavior an interviewer will probe.

This note builds from motivation, through the day-to-day tools (bounds, wildcards, PECS, generic
methods), into the JVM-level internals (erasure, bridge methods, reifiable types, reflection).

---

## Generics motivation and type safety

**Beginner.** Before generics (Java 1.4 and earlier), collections stored `Object`. You had to
downcast on every read, and nothing stopped you from putting the wrong type in:

```java
// Pre-generics: unsafe
List list = new ArrayList();
list.add("hello");
list.add(42);                       // compiles fine — bug hiding here
String s = (String) list.get(1);    // ClassCastException at RUNTIME
```

Generics move that failure from run time to **compile time**:

```java
List<String> list = new ArrayList<>();
list.add("hello");
list.add(42);          // COMPILE ERROR — caught immediately
String s = list.get(0); // no cast needed
```

**Why it matters.** The two headline benefits are (1) **stronger compile-time type checking** and
(2) **elimination of casts**, which makes code both safer and more readable. Generics also enable
generic algorithms that work across types while remaining type-safe.

**Intermediate — the diamond operator.** Since **Java 7 (Project Coin)** you can omit the type
arguments on the right-hand side and let the compiler infer them: `List<String> l = new ArrayList<>();`.
Since **Java 9**, the diamond also works with anonymous inner classes in cases the compiler can
denote. Since **Java 10**, `var` gives local-variable type inference, but be careful:
`var list = new ArrayList<>();` infers `ArrayList<Object>`, not what you usually want.

**Advanced — the naming convention** (not enforced, but universal): `E` element, `K` key, `V` value,
`T` type, `S`/`U`/`V` for additional types, `N` number, `R` return type.

## Type erasure and its consequences

**Beginner definition.** *Type erasure* is the process by which the compiler removes all generic
type information after checking it, replacing type parameters with their **leftmost bound** (or
`Object` if unbounded) and inserting casts as needed. The generated bytecode contains no
`List<String>` — only `List`. This was a deliberate design choice for **migration compatibility**:
generic and pre-generic (raw) code had to interoperate, and existing serialized data / bytecode had
to keep working.

```java
class Box<T> { T value; }
// After erasure, roughly:
class Box { Object value; }

class NumBox<T extends Number> { T value; }
// After erasure the field type becomes Number (the leftmost bound):
class NumBox { Number value; }
```

**Intermediate — the runtime consequence.** At run time all instantiations of a generic type share a
single `Class` object:

```java
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass()); // true — both java.util.ArrayList
```

**Advanced — the concrete things erasure forbids.** Because the type parameter `T` does not exist at
run time, you **cannot**:

| Not allowed | Reason |
|---|---|
| `new T()` | No runtime type; compiler can't know constructor to call |
| `new T[10]` | Cannot create array of a non-reifiable type |
| `x instanceof T` / `x instanceof List<String>` | `T`/type argument gone at run time |
| `(T) obj` as a *checked* cast | Compiles with **unchecked warning**; no real check happens |
| `T.class` | No class literal for a type variable |
| `static T field;` | A static member is shared across all instantiations |
| `catch (MyException<T> e)` | Exception types must be reifiable |
| Overload on erasure-equal signatures | `f(List<String>)` and `f(List<Integer>)` erase to `f(List)` — name clash |

You *can* use unbounded wildcards for `instanceof`: `x instanceof List<?>` is legal because `List<?>`
is reifiable.

**Advanced — heap pollution.** Because casts are unchecked, you can smuggle the wrong type into a
generic container and only discover it later:

```java
List<String> ls = new ArrayList<>();
List raw = ls;          // unchecked
raw.add(42);            // heap pollution — no error here
String s = ls.get(0);   // ClassCastException thrown at this read, far from the cause
```

## Bounded type parameters

**Beginner.** A *bounded type parameter* restricts the types that can be substituted, using `extends`
(which means "is a subtype of", covering both classes and interfaces):

```java
<T extends Number> double sum(List<T> nums) { ... } // T must be Number or a subclass
```

The bound also gives you access to the bound's API inside the method (you can call `Number` methods
on a `T`).

**Intermediate — multiple bounds.** A type variable may have several bounds joined by `&`. **At most
one may be a class, and it must be listed first**; the rest are interfaces:

```java
<T extends Number & Comparable<T> & Serializable> T max(List<T> xs) { ... }
```

The **leftmost bound** is what the type variable erases to (here, `Number`). This is why bound order
matters at the bytecode level.

**Advanced — recursive / F-bounded generics.** A bound can reference the type parameter itself. The
classic example is `Enum` and `Comparable`:

```java
public abstract class Enum<E extends Enum<E>> implements Comparable<E> { ... }

static <T extends Comparable<? super T>> T max(Collection<? extends T> coll) { ... }
```

`<T extends Comparable<? super T>>` (the exact signature of `Collections.max`) means "T is comparable
to itself or to a supertype of itself" — this is the most general, correct bound and a favorite
interview trap versus the naive `<T extends Comparable<T>>`.

## Wildcards and PECS

**Beginner.** A *wildcard* `?` denotes an unknown type. Three forms:

- **Unbounded** `List<?>` — a list of some unknown type; read-only-ish (you can only add `null`).
- **Upper-bounded** `List<? extends Number>` — some subtype of `Number`.
- **Lower-bounded** `List<? super Integer>` — `Integer` or a supertype of it.

**Intermediate — PECS: Producer Extends, Consumer Super.** Joshua Bloch's mnemonic:

- If a parameterized type **produces** values you read out → use `? extends T`.
- If it **consumes** values you write in → use `? super T`.
- If it does both → use an exact type `T` (no wildcard).

```java
// Collections.copy signature illustrates PECS perfectly:
static <T> void copy(List<? super T> dest, List<? extends T> src) { ... }
//                          consumer                producer
```

**Why the asymmetry.** From `List<? extends Number> src` you can safely **read** a `Number` (whatever
the real element type, it IS-A Number), but you **cannot add** anything except `null` — the compiler
doesn't know if the real list is `List<Integer>` or `List<Double>`. From `List<? super Integer> dst`
you can safely **add** an `Integer` (it fits any supertype list), but a **read** only yields `Object`.

```java
List<? extends Number> src = List.of(1, 2, 3);
Number n = src.get(0);   // OK — read
src.add(4);              // COMPILE ERROR — cannot write

List<? super Integer> dst = new ArrayList<Number>();
dst.add(42);             // OK — write
Object o = dst.get(0);   // only Object on read
Integer i = dst.get(0);  // COMPILE ERROR
```

**Advanced — wildcard capture.** The compiler can "capture" a wildcard into a fresh synthetic type
variable (shown in errors as `CAP#1`). A common fix for "capture" errors is a private generic helper
method so the wildcard is captured as a named type parameter:

```java
public static void reverse(List<?> list) { rev(list); }        // delegate
private static <T> void rev(List<T> list) {                    // captures the wildcard
    for (int i = 0, j = list.size() - 1; i < j; i++, j--) {
        T tmp = list.get(i);
        list.set(i, list.get(j));
        list.set(j, tmp);
    }
}
```

**Advanced — wildcards versus type parameters.** Prefer a wildcard when the method doesn't need to
name the type or relate two arguments; use a type parameter when you must refer to the type in more
than one place (e.g., relate the element type of two lists, or a return type to an argument).

## Generic methods and generic classes

**Beginner.** A *generic class/interface* declares type parameters after its name: `class Box<T>`,
`interface Function<T,R>`. A *generic method* declares its own type parameters **before the return
type**, independent of any class type parameters:

```java
static <T> List<T> singletonList(T item) { ... }
List<String> l = ClassName.<String>singletonList("x"); // explicit type witness
List<String> m = singletonList("x");                    // usually inferred
```

**Intermediate — type inference.** The compiler infers method type arguments from the argument types
and the target type (assignment context). **Target-type inference improved in Java 8** so that, e.g.,
`List<String> l = Collections.emptyList();` works without an explicit `<String>` witness, and chained
calls like `stream.collect(toList())` infer correctly.

**Advanced — static context.** A `static` method cannot use the *class's* type parameters (those
belong to instances), so utility methods declare their own: this is why `Collections`/`Arrays`
helpers are generic methods rather than relying on a class parameter.

**Advanced — inference limits.** Inference does not flow through arbitrary expressions; deeply nested
generic calls may still need an explicit type witness. `var` (Java 10) infers the *declared* type of
the initializer, which can surprise you with `Object` element types when combined with `<>`.

## Invariance of generics versus array covariance

**Beginner.** Java **arrays are covariant**: `String[]` IS-A `Object[]`. Java **generics are
invariant**: `List<String>` is **NOT** a `List<Object>`, even though `String` extends `Object`.

**Intermediate — why the difference matters.** Array covariance is unsound and defers a check to run
time (`ArrayStoreException`); generic invariance makes the analogous mistake a compile error:

```java
// Arrays: compiles, blows up at RUNTIME
Object[] arr = new String[3];
arr[0] = 42;                 // throws ArrayStoreException

// Generics: caught at COMPILE time
List<Object> list = new ArrayList<String>(); // COMPILE ERROR — not assignable
```

Every array store performs a runtime type check (the JVM's `aastore` semantics), which is both a
safety net and a small performance cost. Generics need no such check because erasure already proved
safety at compile time.

**Advanced — this is why `new T[]` is banned and generic arrays are messy.** Combining reifiable
covariant arrays with non-reifiable generics would let heap pollution slip past the array store
check, so `new T[n]`, `new List<String>[n]`, etc. are disallowed. The idiomatic workarounds are to
use `List<T>` internally, or create `(T[]) new Object[n]` / `Array.newInstance(componentType, n)` and
accept an unchecked warning (e.g., `ArrayList` and `Arrays.copyOf` do exactly this internally).
Wildcard arrays like `List<?>[]` *are* allowed because `List<?>` is reifiable.

## Bridge methods

**Beginner.** A *bridge method* is a synthetic method the compiler generates to preserve
polymorphism after erasure, most often when a class implements a generic interface or overrides a
generic method with a more specific type.

```java
class MyComparator implements Comparator<String> {
    public int compare(String a, String b) { return a.length() - b.length(); }
}
```

After erasure, `Comparator`'s method is `compare(Object, Object)`. To make dynamic dispatch work, the
compiler adds a synthetic **bridge**:

```java
// generated, marked ACC_BRIDGE | ACC_SYNTHETIC
public int compare(Object a, Object b) {
    return compare((String) a, (String) b); // forwards, inserting the cast
}
```

**Intermediate — covariant return types also generate bridges.** When an override narrows the return
type (legal since Java 5), the compiler emits a bridge with the erased/wider return type that
delegates to the specific one.

**Advanced — observable effects.** Bridge methods are why `Method.isBridge()` and
`Method.isSynthetic()` exist; reflection over a class can reveal *two* `compare` methods. A bridge
method's cast is also where a `ClassCastException` can surface if heap pollution let a wrong-typed
object reach the override.

## Reifiable types

**Beginner.** A type is *reifiable* if its full type information is available at run time — i.e., it
survives erasure unchanged. Non-reifiable types lose information during erasure.

**Reifiable:** primitives; non-generic classes/interfaces (`String`); raw types (`List`);
`List<?>` and other types where **all** type arguments are unbounded wildcards; arrays whose
component type is reifiable (`String[]`, `List<?>[]`).

**Non-reifiable:** `List<String>`, `List<? extends Number>`, `Pair<String,Integer>`, and any
parameterized type with a concrete or bounded type argument; type variables `T`.

**Intermediate — where it bites.** Only reifiable types may appear in `instanceof`, in array creation
expressions, and as component types in some contexts. That is why `o instanceof List<String>` fails to
compile but `o instanceof List<?>` and `o instanceof List` compile.

**Advanced — @SafeVarargs.** Varargs of a non-reifiable type create an array of a non-reifiable
type (`T... args` → `T[]`), which triggers the "possible heap pollution" warning at both the
declaration and call site. **Since Java 7** you can annotate a method with `@SafeVarargs` to suppress
it, but only on methods that don't actually store into or expose the varargs array. It is applicable
to `static`, `final`, and (**since Java 9**) `private` methods — i.e., methods that cannot be
overridden.

## Interaction with reflection

**Beginner.** At run time `List<String>.class` doesn't exist; `list.getClass()` returns plain
`ArrayList.class`. Reflection over *values* cannot recover the erased type argument.

**Intermediate — but declarations keep generic signatures.** The compiler stores generic type info
in the class file's **`Signature` attribute** for classes, methods, and fields. So generic
information that is part of a *declaration* IS recoverable via reflection, through
`java.lang.reflect.Type` and its subtypes: `ParameterizedType`, `TypeVariable`, `WildcardType`,
`GenericArrayType`.

```java
class StringList extends ArrayList<String> {}
Type t = StringList.class.getGenericSuperclass();      // ArrayList<String>
ParameterizedType pt = (ParameterizedType) t;
System.out.println(pt.getActualTypeArguments()[0]);    // class java.lang.String
```

**Advanced — the super type token or Gson `TypeToken` trick.** Because a subclass's generic
superclass is recorded in the `Signature` attribute, you can capture a full generic type at run time
by subclassing an abstract generic holder — this is how Gson `TypeToken`, Jackson `TypeReference`,
and Guice `TypeLiteral` work:

```java
abstract class TypeRef<T> {
    final Type type = ((ParameterizedType) getClass()
        .getGenericSuperclass()).getActualTypeArguments()[0];
}
Type listOfString = new TypeRef<List<String>>() {}.type; // captures List<String>
```

**Advanced — you cannot reflectively defeat erasure on plain instances.** No amount of reflection on
an `ArrayList` *object* tells you it was declared `List<String>`; the info only exists where a
declaration (field, method parameter, extends/implements clause) recorded it in the Signature
attribute.

## Common interview follow-up questions

1. Why did Java choose erasure over reified generics (like C#)? What did it buy (migration
   compatibility) and cost (no `new T[]`, no runtime type args)?
2. Explain PECS with a real signature (`Collections.copy`, `Collections.addAll`). Why can't you
   `add` to a `List<? extends Number>`?
3. Why are arrays covariant but generics invariant? Show the `ArrayStoreException` vs compile-error
   difference.
4. What is a bridge method and when is one generated? How does it relate to `ClassCastException`?
5. What's the difference between `List`, `List<Object>`, and `List<?>`? Which accept an `add(...)`?
6. Give the exact bound for a general-purpose `max` method and explain `Comparable<? super T>`.
7. What is heap pollution and how does `@SafeVarargs` fit in? Which method kinds accept it?
8. Which types are reifiable, and why does `instanceof List<String>` fail to compile?
9. How does Gson/Jackson capture `List<String>` at run time despite erasure?
10. What does `new ArrayList<>()` vs `new ArrayList<Object>()` vs `var list = new ArrayList<>()`
    infer, and where can it bite you?
